# Overhead run, closest to the final topology: the same 4 "3.5 flash hard" environments x 8
# platform rollouts every step, 20 steps, sequences up to 256k tokens. 8 B300 at TP 4 with two
# data-parallel ranks: a 262k-token micro-batch needs about 155 GB on one GPU (it ran out of
# memory on H200's 141 GB), which B300's 288 GB holds.
# No context parallelism: it works (Miles's Qwen3-VL patch passes the rank-local MRoPE position
# ids Megatron-Bridge 0.7 requires), but TP 1 x CP 2 ran out of memory at 256k on B300; see
# ../README.md. Log-probs are computed in 4,096-token fp32 chunks from
# the bf16 logits (~30 GiB at TP 4) and the loss recomputed, so no full-vocabulary fp32 tensor
# exists; the trainer builds no MTP head (see ../README.md). The learning-rate schedule and
# entropy logging below differ too; otherwise this follows ../train_args.txt.
--actor-num-nodes 1
--actor-num-gpus-per-node 8
--calculate-per-token-loss
--rollout-batch-size 12
--global-batch-size 96
--num-rollout 20
--tensor-model-parallel-size 4
--sequence-parallel
--pipeline-model-parallel-size 1
--context-parallel-size 1
--expert-model-parallel-size 1
--expert-tensor-parallel-size 1
--use-dynamic-batch-size
--max-tokens-per-gpu 262144
--recompute-granularity full
--recompute-method uniform
--recompute-num-layers 1
# Reuse FA4 outputs during recompute (~7% less step time, ~14 GiB more peak GPU memory).
--custom-megatron-init-path miles_plugins.proximal.attention_recompute.install
--log-probs-chunk-size 4096
--recompute-loss-function
--skip-actor-forward-only
--advantage-estimator grpo
--kl-loss-coef 0.00
--kl-loss-type low_var_kl
--kl-coef 0.00
--entropy-coef 0.00
# Logs the policy's entropy on trained tokens (train/entropy_loss) without changing the loss: with
# a zero coefficient it is computed detached, from the same logits in the same 4,096-token chunks.
--observe-training-entropy
--eps-clip 0.2
--eps-clip-high 0.28
--optimizer adam
# Start at 2e-5, ramp up over the first 8 updates, then constant. Ceiling 4e-5; fall back to
# 1e-5 on drift alarms. Calibration and alarms: docs/proximal/qwen38-lora-lr.md.
--lr 2e-5
# Megatron counts warmup in samples: Miles makes it --lr-warmup-iters x --global-batch-size and
# each update advances it by that update's samples, so the ramp is 8 updates at any batch size.
# Update k runs at (k-1)/8 of --lr (update 1 only fills Adam's moments), and from update 9 at
# the full --lr. Megatron refuses a warmup that doesn't end within the run: --num-rollout must
# exceed 8.
--lr-warmup-iters 8
--lr-decay-style constant
# The scheduler takes its LR, warmup and decay from these arguments rather than from a checkpoint
# written at another batch size (its iteration counts scale with the batch). The checkpoint
# supplies only the samples trained so far. Until #52 (proximal/lora-scheduler-resume) lands, a
# LoRA resume counts most of them a second time and so skips part of the warmup.
--override-opt_param-scheduler
--weight-decay 0.1
--adam-beta1 0.9
--adam-beta2 0.98
--attention-dropout 0.0
--hidden-dropout 0.0
--accumulate-allreduce-grads-in-fp32
--attention-softmax-in-fp32
--attention-backend flash
--save /state/checkpoints
--save-interval 1
--seed 42
--use-wandb
--wandb-project miles-qwen38
--wandb-group qwen38-27b-overhead
# Kernel tuning and compilation can hold one rank for minutes; 10 min killed run 007.
--distributed-timeout-minutes 60
